# CI Hygiene and Trust Boundaries

## Purpose

This document separates the repository's CI/CD workflows by responsibility, trust boundary, and evidence value.

The goal is not to delete historical automation. The goal is to prevent preserved implementation workflows from creating false-red signals, unnecessary credentials, duplicate publishing, or accidental authority in the current Infrastructure-as-a-Product program.

> **IaaS is what we buy; infrastructure-as-a-product is what we build.**

CI should support that product mental model: deterministic validation is routine and credential-free where possible; privileged publishing and external archival occur only in trusted contexts; preserved V1 workflows remain available without being mistaken for mandatory architecture.

## Workflow classes

| Class | Purpose | Default trigger | Credentials / write authority |
|---|---|---|---|
| Required validation | Syntax, tests, policy, product contracts, documentation, security checks | Pull request | Read-only wherever possible |
| Trusted publish | Package/image publication, signing, attestations | `main` or explicit dispatch | Narrow write and OIDC permissions |
| External integration | Cloud archival, deployment, provider-specific proof | Explicit dispatch or protected environment | Federated cloud identity only |
| Preserved compatibility | Historical Arc/Terraform/docs patterns retained as IP | Explicit dispatch | None unless the historical operation itself requires it |

## Principles

### 1. Pull requests do not publish mutable runtime artifacts

Pull requests may build images and validate Dockerfiles, but they do not push `latest` tags, sign production-facing artifacts, archive to cloud storage, or apply infrastructure.

Publishing belongs to a trusted `main` or manually approved workflow with explicit permissions.

### 2. CI permissions are granted at the narrowest useful scope

A validation job does not receive `packages: write` or `id-token: write` merely because a publishing job in the same repository needs them.

Write permissions belong to the specific trusted job that uses them.

### 3. Generated evidence is not assumed to exist in source control

OSCAL `assessment-results` and similar runtime evidence are generated by the evidence pipeline, validated in that pipeline, and uploaded as workflow artifacts or to an approved external evidence store.

A pull request must not fail because a generated evidence file is intentionally absent from the Git repository.

### 4. External archival is distinct from evidence generation

The repository can prove that it generated a structurally valid evidence artifact without requiring Azure, AWS, GCP, OCI, TFE, or other external credentials.

Uploading evidence to an immutable external store is a separate trusted operation.

### 5. Secret scanning must fail closed without requiring an organization license

The canonical Gitleaks workflow uses the pinned CLI container rather than an organization-license-dependent GitHub Action.

Before scanning the repository, it runs a canary containing a synthetic token and requires the detector to identify it. A detector that silently stops matching known secret patterns therefore fails the workflow before repository results are trusted.

The older `secret-scan` workflow is retained as a manual compatibility wrapper around the canonical scan rather than running a second independent scanner on every pull request.

### 6. The Terraform V1 toolchain remains valid but bounded

The preserved Terraform workflows use Terraform **1.8.5**, the final valid patch release in the intended 1.8 line. The former `1.8.6` pin could not resolve and was a CI defect, not an architectural signal.

Terraform/TFE workflows remain implementation assets. Correcting their CI does not make Terraform Enterprise a mandatory product-control-plane dependency.

### 7. Dedicated security tools remain dedicated CI concerns

TFLint, Checkov, Conftest, Trivy, Cosign, and evidence tooling remain in purpose-built workflows.

Developer pre-commit bootstrap is limited to basic file hygiene and syntax so it does not duplicate full-repository security scans or depend on stale third-party pre-commit manifests.

### 8. One public documentation publisher

`docs-pages.yml` is the canonical publisher for the curated program documentation site.

Older documentation workflows are retained as manual preview or compatibility builds and upload artifacts rather than competing to deploy GitHub Pages.

This preserves historical documentation without allowing multiple workflows to race for the same public site.

## Current workflow ownership

### Required pull-request baseline

Examples include:

- unit and Python tests;
- `pre-commit` changed-file hygiene;
- Mermaid lint;
- curated MkDocs build;
- marketplace metadata validation;
- dependency review;
- Terraform validation where preserved HCL is affected;
- Checkov, TFLint, Conftest, and Trivy security/policy checks;
- Gitleaks secret scanning with detector canary; and
- bounded composite-AI/security evidence checks.

These checks should not require cloud or TFE credentials.

### Trusted publication

Container publishing, provenance, SBOM publication, and Cosign signing are allowed only outside pull-request context.

The canonical GHCR repository path is normalized to lowercase:

```text
ghcr.io/saabolimpactventure/ai-powered-infrastructure-as-a-product
```

Pull requests validate image builds without publishing.

### External or credential-dependent operations

Examples include:

- Azure immutable evidence archival;
- cloud deployment workflows;
- provider-specific live proof;
- protected-environment Terraform apply; and
- future live AWS/GCP sandbox experiments.

These operations are intentionally not required to establish a credential-free pull-request baseline.

### Preserved compatibility workflows

Historical workflows remain useful for demonstrating prior implementation patterns and for controlled manual use.

They should be labeled clearly and must not become required checks merely because they remain in the repository.

## Evidence interpretation

A green required baseline proves that the repository-owned validation path is internally coherent.

It does **not** prove:

- live AWS/GCP/Azure/OCI provisioning;
- external identity federation;
- production authorization;
- TFE value or non-value;
- successful immutable cloud archival; or
- live composite-AI model performance.

Those remain separate evidence gates in the program roadmap.

## Relationship to the product thesis

CI hygiene supports the larger architecture by keeping implementation mechanisms replaceable.

A Terraform workflow can be healthy without becoming the product. A Crossplane workflow can be healthy without making Crossplane universal. A composite-AI evaluation can be healthy without giving AI execution authority.

The product boundary remains stable while the implementation and evidence mechanisms compete on measured value.
